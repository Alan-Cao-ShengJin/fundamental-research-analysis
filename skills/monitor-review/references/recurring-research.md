# Durable recurring research and follow-up

Use when retaining follow-up work or preparing an authorized recurring review. A saved work item must be useful to a later session that cannot see the original conversation. The host's actual scheduler and authorization determine execution; this reference does not install a service or grant messaging/trading permissions.

## Write one self-contained work definition

Reuse the existing issuer/theme dossier, issue and model IDs. Maintain a canonical task definition separately from dated run results. Do not create a new issue every time wording changes or overwrite a failed run with a later success. Distinguish ordinary open research, a proposed recurrence and an acknowledged scheduled job.

Include the information needed to perform the work, scaled to the task:

- The research question, exact issuer/share class or universe, horizon and why a result could change the decision.
- Baseline evidence, thesis and model/workbook locations and versions, including how to resolve the current approved baseline at run start. Preserve the prior version for comparison.
- Permitted source routes, retrieval/cutoff/freshness rules, materiality thresholds and the missing-data behavior. Do not put credentials in the task.
- The concrete reads/calculations, dependencies to refresh, required output locations and the checks needed before replacing current outputs. A numerical company revision follows the model-revision and Excel delivery contracts.
- If recurrence is authorized: cadence or event, explicit timezone, market/holiday alignment, expiry, budget/timeout and supported overlap/missed-run policy. Do not assume a host implements a policy that has not been inspected.
- The completion condition and escalation path. Define which result merits a human update, its authorized destination and how delivery is acknowledged. Unchanged research can produce a small dated local record without a redundant notification when the user's delivery instructions allow it.

Write conditions in the work definition unless the actual scheduling service provides verified condition semantics. Avoid a prompt that says only "check this again" or relies on the conversation to identify "the model."

## Execute a review, not a report rewrite

Read the latest completed run and approved baseline. Check data/worker health first, obtain relevant new observations and compare source identities, reporting scope and availability before judging change. Feed new evidence through semantic assumptions, affected calculations, audit, valuation and the scoped conclusion. Preserve source snapshots and old forecasts. Refresh linked prose and charts only where dependencies changed.

Select the company's analytical mode using [request routing](../../research-cycle/references/request-routing.md); cadence does not determine it. Regular reviews preserve the operating forecast unless concrete evidence supports a change. Major earnings/catalyst updates preserve and evaluate prior forecasts before recalibration. Retain this routing instruction in self-contained recurring company tasks.

For a valid no-change result, retain the baseline version, observations checked and reason no revision followed. Missing data, an overdue filing or failed calculation is not a clean no-change result. Record last success, failure scope and a specific next recovery action; bounded retries follow the host's policy and task budget.

Where another session or a user may edit the workbook, recheck its fingerprint before replacing it. Respect concurrent work, preserve user edits and retain an output/version record that ties evidence, calculation and communication together. A linked task or paused dependency does not prove that another process completed it.

## Record operational state separately

Keep work status/priority separate from schedule and delivery health. Report a job as active only with an actual scheduler acknowledgement; retain its ID, next run/timezone and last-run result where available. Check delivery separately from generation: a report file or successful calculation does not establish that a notification reached anyone. An unknown or failed acknowledgement remains unknown or failed.

Creating or revising these skill instructions does not activate monitoring. When a user requests only a review plan, leave the job proposed. When the user authorizes recurring work and a suitable service is available, make the task concrete, register it within that scope and verify the returned state. Use the host's supported controls for updates, pauses or expiry; do not copy another product's CLI, issue-file format, model settings or automatic-commit behavior.
